# Spec: v0.4.1 evidence calibration

## Assumptions

1. v0.4.1 improves the evidence supplied to the existing Impact × Urgency matrix; it
   does not change that matrix or its priority policy.
2. The organisation may later supply independently labelled, anonymised tickets, but
   no real ticket text is committed to this repository.
3. The release remains a local-only, dependency-free static application. It does not
   add a grammar parser, a model, a backend, network calls, or persistent storage.
4. A human analyst may confirm a business consequence, but automatic rules must not
   invent one from a system name, senior requester, or a claimed priority.

## Objective

Make priority errors diagnosable at the fact level and improve the engine's ability to
tell the difference between a technical symptom and the business process it disrupts.
The user should be able to see whether scope, consequence, deadline, workaround, or
risk is explicitly stated, inferred, or still unknown; confirm a missing consequence;
and receive the same explainable P1–P4 result path as today.

## Tech stack

Vanilla JavaScript ES modules, static HTML/CSS, and the dependency-free Node test
harness. All ticket analysis stays in the browser. The offline evaluator reads only a
local JSON corpus passed on the command line.

## Commands

- Full behavioural tests, privacy scan, evaluator tests, and schema fixture:
  `npm test`
- Evaluate an approved local corpus:
  `node tests/evaluate.mjs tests/fixtures/accuracy-corpus.json`
- Syntax check changed module(s): `node --check <changed-js-file>`
- Source hygiene: `git -c core.whitespace=cr-at-eol diff --check`

## Project structure

- `js/engine/`: pure detectors and scoring; add a narrowly scoped consequence fact
  detector here if existing `analyzer.js` helpers cannot remain small.
- `js/data/phrases.js`: auditable language patterns only.
- `js/engine/analyzer.js`: combines detected and analyst-confirmed facts, builds
  questions, and runs priority-change simulations.
- `js/engine/impact.js`, `js/engine/urgency.js`, `js/engine/confidence.js`: score
  decision-relevant facts, never emit a priority.
- `js/ui/refine-controls.js`, `index.html`: analyst confirmation controls.
- `tests/tests.js`: positive and nearby-counterexample behavioural tests.
- `tests/evaluate.mjs`, `tests/evaluate.test.mjs`: local corpus validation and metrics.
- `tests/fixtures/accuracy-corpus.json`: schema example only, never a production
  accuracy claim.

## Code style

Keep facts pure, explicit about provenance, and separately score them:

```javascript
return {
  consequence: 'blocked',
  process: 'attendance marking',
  source: 'explicit',
  evidence: [{ quote: 'teachers cannot mark the roll', meaning: 'Attendance marking is blocked' }]
};
```

Detectors establish facts; impact and urgency consume those facts; only
`priority-matrix.js` maps the resulting values to P1–P4. An analyst confirmation is
labelled `source: 'manual'`; an inferred configured-system consequence is labelled
`source: 'inferred'` and must remain visibly distinct from requester wording.

## Testing strategy

- Start every changed behaviour with a failing test and a nearby counterexample.
- Test fact extraction independently of the final priority, then assert impact,
  urgency, priority, evidence provenance, and follow-up ordering end-to-end.
- Extend the evaluator schema with optional expected facets and report accuracy only
  where that facet is labelled. Do not calculate or publish a production percentage
  from the shipped schema examples.
- Include counterexamples for generic wording: a named critical system, a how-to, or
  an asserted urgency must not manufacture a blocked business process.
- Run the complete suite and privacy scan after each implementation slice.

## Boundaries

- Always: preserve local-only handling, explainability, the assessment-status boundary,
  manual override provenance, and the authoritative matrix.
- Ask first: change matrix policy or weights, add dependencies, network calls,
  storage, real ticket data, or a new externally supplied corpus.
- Never: infer a business consequence merely because a system is important; count
  declared urgency as evidence of impact; expose ticket text in evaluator output; or
  silently convert an analyst control's displayed value into confirmed evidence.

## Success criteria

- The evaluator accepts optional expected values for the decision facets and reports
  coverage, accuracy, and mismatches for each labelled facet without requiring any
  ticket text in its report.
- A first-class consequence result distinguishes `unknown`, `impaired`, and `blocked`,
  records the named process when known, and exposes `explicit`, `inferred`, or `manual`
  provenance and evidence.
- Explicit business-process wording changes scoring only through documented impact and
  urgency contributions; generic technical failure wording retains existing behaviour.
- The refinement panel allows an analyst to confirm the consequence level, survives
  recalculation, and is shown in the reasoning and printed result as a manual fact.
- The missing-information panel asks about a business consequence when it is the
  highest-value unknown, while retaining the six-question cap and priority-change
  simulation ranking.
- New contrast tests and the full suite are green; release documentation identifies
  v0.4.1 and makes no unsupported accuracy claim.

## Open questions

- Which anonymised historic tickets and human-review procedure will define the first
  calibration corpus? This is required before tuning weights, but not before building
  the schema and diagnostics.
- Should a confirmed `impaired` process have a fixed impact contribution, or should it
  remain explanatory until an approved corpus demonstrates a safe weight? The default
  implementation should use the smallest policy-preserving contribution and document
  it for review.
